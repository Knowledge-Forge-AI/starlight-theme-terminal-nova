## A gallery for real documentation

The gallery is intentionally made from ordinary Starlight content primitives. Cards summarize a
decision, tabs keep related views together, file trees orient a reader, tables compare exact
choices, and callouts mark a boundary without interrupting the main explanation. These are
consumer-facing examples, not a replacement component library.

## Consumer configuration

This is the published integration surface. The plugin is a function with no runtime accent or
family argument; customization happens in Starlight's own configuration and in consumer-owned CSS.

```javascript title="astro.config.mjs" {3}
import { defineConfig } from 'astro/config';
import starlight from '@astrojs/starlight';
import terminalNova from '@knowledge-forge-ai/starlight-theme-terminal-nova';

export default defineConfig({
  integrations: [
    starlight({
      title: 'Example Documentation',
      plugins: [terminalNova()],
      customCss: ['./src/styles/site.css'],
    }),
  ],
});
```

The theme registers package styles before the paths listed in `customCss`. A consumer can also
override a Starlight component explicitly:

```javascript title="astro.config.mjs: component override"
starlight({
  components: {
    PageTitle: './src/components/ConsumerPageTitle.astro',
  },
});
```

The override is site-owned and wins over the theme's default `PageTitle` mapping. It does not
change the package's license or its protected identity artwork.

## Code editor and terminal

The package supplies light and dark syntax themes and bounded frames through Expressive Code.
These fences show the two common presentation modes:

```javascript title="src/styles/site.css: consumer token adjustment" {2} ins={5} del={4}
:root {
  --tfsl-color-accent-base: #69d3e4;
  --tfsl-color-focus: var(--tfsl-color-accent-base);
  color-scheme: light dark;
}
```

```bash title="Terminal: build a consumer site" frame="terminal"
$ npm run build
[site] Astro builds the Starlight project with Terminal Nova styles
[site] Package-local assets remain available to the generated site
```

The command is a representative consumer action. The theme package does not prescribe a site's
hosting command or deployment provider.

## Theme-authoring example: generation-time accents

This second example belongs to the theme-generation side of the system, not to the published
consumer API:

```javascript title="Generator-side example" {2} ins={5} del={4}
import { compileTheme } from '@knowledge-forge-ai/theme-forge-stellar-loom';

const spec = await loadThemeSpec('terminal-nova.theme.json');
// The accent is selected while generating a target output.
const compiled = compileTheme(spec, { accent: 'orange' });
```

The existing `orange` and `cyan` accent variants are generation-time choices. A consumer cannot
turn the published 0.5.0 plugin into a twelve-appearance runtime selector by passing an `accent`
option. The six family stylesheets are separate opt-in package resources; they do not add runtime
selection or persistence.
For the broader preview boundary, read [Appearance Families](/docs/appearance-families/).

The published consumer boundary described here is 0.5.0. The 0.4.0 Forge Console release remains
historical context, while the current package adds opt-in family stylesheets without changing the
plugin's no-runtime-picker contract.

## Callout asides

:::note[General note]

Keep a callout close to the decision it explains. A reader should not have to search another page
to discover that a code snippet is a consumer example or that a family route is a static demo
preview rather than a runtime picker.

:::

:::tip[Best practice]

Prefer a small, explicit component override to copying the theme's generated implementation into a
site. The consumer keeps ownership of the change while the package can continue to receive updates.

:::

:::caution[Boundary condition]

The published package includes local theme resources and six opt-in family stylesheets; the six demo
SVGs and static gallery belong to this consumer demo. Neither adds a persisted family-selection or
save/reopen flow to the plugin.

:::

<Aside type="note" title="Callout semantics">

Use a note for context, a tip for a recommended practice, and a caution for a limitation that
could change how a reader adopts the example. The surrounding text remains the source of detail.

</Aside>

## Component reference table

| Component or pattern | Starlight surface | Good use in a product page |
| :--- | :--- | :--- |
| Cards | `Card`, `CardGrid` | Summarize products, targets, or status with short copy |
| Asides | `Aside` and `:::note`/`:::tip` directives | Explain a boundary beside the relevant section |
| Badges | `Badge` | Mark a published, preview, or separate-target distinction |
| Tables | Markdown table syntax | Compare versions, capabilities, and responsibilities |
| Tabs | `Tabs`, `TabItem` | Keep alternate layouts or implementation notes together |
| File tree | `FileTree` | Show where a consumer owns configuration and content |
| Code fences | Expressive Code defaults | Present commands and configuration with a clear frame |

## Building a long page without losing the reader

Long technical pages work best when each section answers one question. Start with the outcome,
show the smallest useful example, then explain the edge or ownership boundary. A table can hold
exact mappings that would make a paragraph unwieldy, while a callout can keep a limitation visible
without turning every sentence into a warning. This gallery deliberately repeats the same content
ideas—installation, customization, target choice, and identity handling—in different Starlight
primitives so a site author can compare the reading experience.

When a page grows beyond one task, split it into linked routes rather than hiding a second manual
inside a tab. The demo's navigation keeps the front door, architecture, workflow, components,
appearance families, getting started, and brand guidance as separate concerns. That structure is
also friendly to deep links and card-style pagination.
