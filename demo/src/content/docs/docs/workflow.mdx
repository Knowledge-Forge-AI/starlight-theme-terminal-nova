## From profile to page

Terminal Nova is one target in a wider Theme Forge workflow. A maintained theme profile describes
roles such as page, panel, border, focus, code, and accent. Stellar Loom resolves that profile into
target output; STTN packages the Starlight adapter, styles, components, middleware, and metadata;
an Astro consumer then supplies its own content and site configuration.

### The three paths

1. **Stellar Burst → SVG:** editable scene data becomes a local vector asset. The SVG is a
   production output; the scene remains the maintainable source when a graphic needs revision.
2. **Stellar Loom → package:** a theme specification becomes target-specific CSS, component
   modules, code defaults, and package metadata. STTN is the Astro/Starlight target; CTTN is the
   sibling shadcn/Tailwind target.
3. **Nebular → review context:** the desktop workbench can show a profile in a real editing or
   preview context. A Nebular preview is useful for design work, but it is not a prerequisite for
   serving an STTN site.

:::tip[Deterministic resources]

The published package carries package-local resources and does not generate runtime network
requests. The demo's SVGs are local examples; a site can add its own assets through ordinary Astro
content and public files.

:::

## A consumer's workflow

The practical path for a documentation author is intentionally short:

1. Install the published versions in [Getting Started](/docs/getting-started/).
2. Register `terminalNova()` in `astro.config.mjs`.
3. Add pages, navigation, and site-owned styles in the consumer project.
4. Use the built-in light/dark Starlight mode and code frames, then add a component override only
   where the site's information architecture needs one.
5. Build and deploy through the consumer's existing Astro process.

```js title="Consumer configuration"
import { defineConfig } from 'astro/config';
import starlight from '@astrojs/starlight';
import terminalNova from '@knowledge-forge-ai/starlight-theme-terminal-nova';

export default defineConfig({
  integrations: [
    starlight({
      title: 'Example Docs',
      plugins: [terminalNova()],
      customCss: ['./src/styles/site.css'],
    }),
  ],
});
```

The theme's defaults are loaded before consumer CSS, so `site.css` can adjust a token or add a
site-specific component treatment without copying the package's generated styles.

## What belongs where

| Input or result | Maintained by | Consumer-facing meaning |
| :--- | :--- | :--- |
| Theme profile and resolved roles | Theme Forge source | The design intent from which targets are generated |
| SVG scene source and output | Stellar Burst path | A local, reproducible illustration or decoration |
| STTN package output | Stellar Loom target | Installable Astro/Starlight theme resources |
| MDX page and navigation | Site author | Product information and route structure |
| Custom CSS/component override | Site author | A deliberate local adaptation with consumer precedence |
| Appearance-family preview | Shared development work | Direction for future outputs, not an npm 0.4.0 runtime feature |

<Aside type="caution" title="Generation is not runtime selection">

The existing orange and cyan accents are generation-time outputs. Calling `terminalNova()` in a
published consumer does not select among six families or twelve appearances, persist a family choice, or start a
compiler. See [Appearance Families](/docs/appearance-families/) for the exact published boundary.

</Aside>

## Boundary isolation summary

| Boundary | Requirement | What this demo illustrates |
| :--- | :--- | :--- |
| Package identity | Install a published STTN package | Versioned npm install and plugin registration |
| Site ownership | Keep content and custom CSS in the consumer | MDX pages, `customCss`, and explicit overrides |
| Asset locality | Serve demo art from the consumer's public files | Local SVG figures with accessible descriptions |
| Code presentation | Keep examples near the explanation they support | Expressive Code fences with titles and frames |
| Product relationship | Keep STTN, CTTN, and Nebular roles distinct | Target, sibling target, and authoring workbench |

## Read the figures as a maintainer

The editable input is not the same artifact as the package output. When a page references
`/art/engine-workflow.svg`, it is consuming a finished local asset. When a consumer installs the
STTN package, it is consuming target output produced elsewhere. Keeping those seams visible makes
it possible to update a source profile or illustration without treating generated files as the
design brief.

The same rule applies to appearance families. The six-family collection is useful for design
exploration and future target work, but it must not be described as a capability already present in
the 0.4.0 plugin. A site can document a preview while continuing to install the published baseline.
