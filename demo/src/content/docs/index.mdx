## A quiet forge for technical ideas

Terminal Nova is a documentation theme for **Knowledge Forge AI** and personal writing: a place to explain a system, keep a working notebook, and leave the next reader a clear path. Warm surfaces, precise dividers, and a measured accent bring the workshop into the page. The words stay in a familiar proportional typeface; commands keep their own disciplined rhythm.

This is an independent first-party theme built with Stellar Loom for [Astro Starlight](https://starlight.astro.build). It does not continue the legacy Terminal Nova fork. The Nova Ingot is the approved project mark; the interface is new work.

:::note[Private working candidate]
Forge Console is the provisional selection. Nova Observatory remains available for comparison. This package has not been registered or publicly released, and the selection does not represent final aesthetic approval.
:::

## Start at the command line

Keep the theme specification in version control. Generate into a fresh directory, pack it, then install the local archive. The explicit `--ignore-scripts` option keeps installation separate from executing a site build.

```sh title="local session"
tfsl validate terminal-nova.theme.json --strict-contrast
tfsl generate terminal-nova.theme.json --package package-metadata.json --out ./generated
cd generated
npm pack
# In your documentation site:
npm install --ignore-scripts /absolute/path/to/theme.tgz
```

## Read, inspect, return

Good technical writing has several speeds. A new reader needs enough context to understand why a decision exists. A returning maintainer needs an anchor, a short example, and an accurate boundary. Neither should have to navigate a wall of simulated terminal output to reach a paragraph.

The reading column therefore leaves room for an explanation without stretching a sentence across the screen. Navigation stays visible on a wide display and moves into a menu on a phone. Headings carry the structure, while tables and code may scroll inside their own containers. Follow the [design notes](/design/) for the alternatives and return through the sidebar.

### A useful decision record

Start with the question that made the decision necessary. Describe the observable behavior, then show the smallest example that makes the contract concrete. Put uncertainty next to the claim it limits. When you return months later, a clear boundary is more useful than a confident adjective.

Use `themeDigest` to identify the semantic input and `outputDigest` for the emitted CSS. A packet binds its contents; it does not authenticate the author. A preview helps judge a candidate; adopting it creates an unsaved draft. Saving and generating remain separate actions.

:::tip[Make the next step explicit]
Use headings as destinations. Link to the section that resolves a question, and keep one runnable example near the explanation it supports.
:::

:::caution[Keep the boundary visible]
A local package is a working artifact. Public composition, signing, SBOM generation, and release execution still need their owning release workflow.
:::

## Leave a useful trail

Before sharing a result, record what actually ran: the specification, package metadata, adapter, and local build. Keep the image beside the identity of the design it depicts. A small reproducible example earns its place by helping someone make the next change with confidence.

1. Read the brief and its constraints.
2. Compare both modes at a comfortable and a narrow width.
3. Inspect diagnostics, annotate the candidate, and save deliberately.

That is the working rhythm of Terminal Nova: write, inspect, refine.
