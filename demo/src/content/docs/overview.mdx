## A theme target, not an application shell

Terminal Nova is the Starlight target in the Theme Forge family. It packages a visual system,
layout chrome, component integrations, and code presentation defaults for an Astro documentation
site. It does not replace Starlight's content model, run a compiler in the browser, or provide the
application behavior that belongs to your product.

The package is published as `@knowledge-forge-ai/starlight-theme-terminal-nova@0.4.0`. Its demo is a
consumer project pinned to Astro 7.3.3 and Starlight 0.42.0 so the adoption path is concrete. Start
with [Getting Started](/docs/getting-started/) if you are adding it to a new site.

This source tree also prepares an unreleased 0.5.0 candidate. It does not change the published
0.4.0 install guidance or claim registry availability before a separate publication decision.

## The four boundaries

| Boundary | Owns | Does not own |
| :--- | :--- | :--- |
| Content | Markdown/MDX pages, links, examples, and your information architecture | Theme generation or product data |
| Starlight adapter | Plugin registration, package-local CSS, component mapping, middleware, and code defaults | Your route content or business logic |
| Shared Theme Forge source | Theme profiles, resolved tokens, and target-specific generated outputs | Runtime family switching in a 0.4.0 consumer |
| Consumer site | Site CSS, content, custom components, metadata, and deployment | The license or approved treatment of protected identity artwork |

This separation lets a documentation author customize a page without editing generated theme
files. It also makes it clear where a request belongs: STTN for an Astro/Starlight site, CTTN for a
shadcn/Tailwind consumer, and Nebular Fusion for desktop authoring and preview workflows.

## Architectural principles

1. **Readable first:** system-sans prose, a proportional column, and clear heading hierarchy keep
   long technical pages usable.
2. **Disciplined chrome:** navigation and code frames borrow terminal cues while leaving the
   document itself in control of the reading flow.
3. **Resolved tokens:** light and dark surface roles are emitted by the theme output rather than
   asking a page to recalculate them at runtime.
4. **Consumer precedence:** a site's custom CSS and explicit Starlight component overrides load
   after the theme defaults.
5. **Local by default:** package assets and the demo's SVG scenes are local; the package does not
   generate runtime network requests.

## A day in the life of an STTN page

The consumer supplies an MDX page and an Astro/Starlight configuration. Starlight loads the
Terminal Nova plugin, which registers the package styles and default component map. During site
build, the page is composed with those defaults and any consumer-owned overrides. At request time,
the site serves the generated page and package-local assets; it does not invoke Stellar Loom or
Nebular.

```text
MDX page + Starlight config
        |
        v
Terminal Nova plugin  --->  CSS layers, code defaults, components, middleware
        |
        v
Astro build           --->  static or server-rendered Starlight site
```

:::tip[Keep generated output at the boundary]

If you need a different family or a new token role, change the maintained profile and regenerate
the target output through the appropriate Theme Forge path. If you need a site-specific spacing or
component adjustment, use your project's `customCss` or a Starlight component override. Do not
hand-edit package `dist/` files as a customization strategy.

:::

## Published behavior and the next collection

Version 0.4.0 is the published Forge Console baseline. It carries the orange primary output and
Starlight-compatible light/dark tokens. The source retains a separate cyan generation path, but
the installed plugin does not expose it as a runtime option.
The shared next-cycle collection is broader: six visual families with a light and dark appearance
for each. That collection is a development preview, not a capability claim about the current npm
package. In particular, 0.4.0 does not ship a twelve-entry appearance picker, persisted family
preferences, or a working save/reopen appearance workflow.

The distinction matters for product relationships:

- **Nebular Fusion** can author, compare, or preview shared profiles as its desktop workbench.
- **STTN** consumes a generated Starlight target and gives documentation authors a stable package
  integration.
- **CTTN** consumes the same design intent in a shadcn/Tailwind target with different component
  mappings.

The shared family catalog can grow without changing the fact that a published STTN consumer is a
normal Astro/Starlight project with ordinary source, build, and deployment ownership.
